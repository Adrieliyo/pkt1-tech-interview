## Project overview

.NET 8 REST API (`ShipmentTracker.sln`) managing shipments for a parcel delivery company, built in layers following Clean Architecture. Domain modules so far: **Shipment**/**ShipmentEvent**/**DeliveryAttempt** (tracking, status transitions including an `OutForDelivery` phase, a lifecycle-event log, and failed-delivery-attempt records), **Branch/BranchSchedule** ("Branches & Hubs" — physical locations and their weekly operating hours), **Employee/Vehicle** ("Employees & Vehicles" — operational staff and fleet, each referencing `Branch` by FK), **Customer** ("Customers & Accounts" — a type-discriminated `Individual`/`Business` entity, see TPT note below), and **Order** ("Orders" — a shipment request referencing `Customer` and optionally `Branch`, whose central operation converts a confirmed Order into a `Shipment` + its first `ShipmentEvent`).

## Commands

```bash
# Build the whole solution
dotnet build ShipmentTracker.sln

# Run the API (Swagger UI at /swagger in Development)
dotnet run --project ShipmentTracker.Web

# Create the database (once), then apply migrations
# (connection string: ShipmentTracker.Web/appsettings.json -> ConnectionStrings:DefaultConnection)
dotnet ef database update --project ShipmentTracker.Infrastructure --startup-project ShipmentTracker.Web

# Add a new migration after changing an entity/EF configuration
dotnet ef migrations add <Name> --project ShipmentTracker.Infrastructure --startup-project ShipmentTracker.Web
```

There is no automated test project in this solution — validation is done manually via Swagger/HTTP. Each feature under `specs/` has a `quickstart.md` with the manual scenarios to run against the live API.

## Architecture

Four projects, one-directional dependency flow — never invert these:

- **`ShipmentTracker.Core`**: entities, DTOs, enums, interfaces (`Interfaces/Repositories`, `Interfaces/Services`). No dependencies on any other project in the solution.
- **`ShipmentTracker.Infrastructure`**: EF Core `AppDbContext`, entity configurations (`Data/Configurations`), migrations, repository implementations. Depends only on `Core`.
- **`ShipmentTracker.Services`**: business logic (`*Service` classes), FluentValidation validators (`Validators/`), AutoMapper profiles (`Mappings/`). Depends only on `Core`.
- **`ShipmentTracker.Web`**: composition root — controllers, `Program.cs` (all DI registration and CORS/Swagger setup). The only project allowed to depend on all three of the above.

Each domain module (e.g. `Shipment`, `Branch`, `Employee`, `Vehicle`) repeats the same shape across the four layers: entity + DTOs + `I<X>Repository`/`I<X>Service` in Core, an `<X>Repository : BaseRepository<X>` in Infrastructure, an `<X>Service` + validators + a mapping profile in Services, and an `<X>Controller` in Web. A feature can bundle more than one such module (e.g. "Employees & Vehicles" is `Employee` + `Vehicle` as two independent tracks that only share a FK to `Branch` — each still gets its own full per-layer file set, and can be built/tested separately). `Customer` deviates from the flat-entity shape via TPT inheritance (see below). `Order`'s central operation (`ConvertToShipmentAsync`) is additionally allowed to touch another module's repository (`ShipmentRepository`) directly through `IUnitOfWork` — this is the one sanctioned exception to "a module only touches its own repository," and only because the operation's entire purpose is creating that other module's entity; it still never touches `AppDbContext`/`DbSet` directly, and the touched entity (`Shipment`) itself only gained one nullable FK column rather than being restructured. `DeliveryAttempt` (module `007`) has no service/controller of its own — like `BranchSchedule`, it's a service-managed child concept, only ever written internally alongside a `ShipmentEvent`, sharing `ShipmentEventService`/`ShipmentEventController` instead.

Established conventions — follow them rather than introducing a competing pattern for the same concern:

- **Repository + Unit of Work**: generic `IBaseRepository<T>`/`BaseRepository<T>` (supports filter/orderBy/paging via `GetAsync`). Each entity gets its own `I<Entity>Repository : IBaseRepository<Entity>`, exposed as a lazily-instantiated property on `IUnitOfWork`/`UnitOfWork` (e.g. `unitOfWork.BranchRepository`). No project other than `Infrastructure` touches `AppDbContext`/`DbSet` directly. If a repository needs no query beyond what the generic base already offers, leave its interface empty (`IEmployeeRepository : IBaseRepository<Employee> { }`) rather than adding methods speculatively.
- **AutoMapper is output-only**: `CreateMap<Entity, Dto>()` profiles map entity → response DTO. Creating an entity from an input DTO is done by hand in the `Service` method (see `ShipmentService.CreateShipmentAsync`, `BranchService.CreateBranchAsync`) — don't mix `_mapper.Map` into entity construction.
- **FluentValidation covers structural rules only** (required fields, formats, enum validity, numeric ranges) and is invoked manually inside `Service` methods (not wired into the MVC pipeline) — never as an async validator with a repository injected. Rules that need a database round-trip (a referenced entity must exist/be active, a field must be globally unique) are checked directly in the `Service`, *after* structural validation, with both sets of failures merged into one list. On failure the service throws (`FluentValidation.ValidationException` carrying the full merged error list for multi-field DTOs; a plain exception for single-rule checks like status transitions); the controller catches it and returns `400` with the error list. See `EmployeeService`/`VehicleService`'s shared private `ValidateBusinessRulesAsync(..., currentId)` helper — reused by both `Create` (`currentId: 0`, which never matches a real identity-generated id) and `Update` (`currentId: id`, to exclude the record being edited from its own uniqueness check) instead of duplicating the checks.
- **Enums are persisted as strings** (`HasConversion<string>()` in the entity configuration) so the database stays human-readable regardless of enum member order.
- **Foreign keys to entities that are never hard-deleted** (e.g. `BranchId` on `Employee`/`Vehicle`) use `.OnDelete(DeleteBehavior.Restrict)` and stay **unidirectional** — don't add a back-reference collection (`ICollection<Employee>`) to the referenced entity (`Branch`) unless a real use case needs to load "all children of X" through X itself; query the child's own repository filtered by the FK instead.
- **List endpoints are paginated** (`Shipment`, `Branch`, `Employee`, `Vehicle` all follow this): `PagedResult<T>` (`Core/DTOs/PagedResult.cs`), `page`/`pageSize` query params (`[Range(1, int.MaxValue)]`), a per-service `MaxPageSize = 50` clamp (not a `[Range]` upper bound — clamping, not rejecting), ordered `OrderByDescending(x => x.CreatedAt)`, and the same 4 response headers (`X-Total-Count`, `X-Page`, `X-Page-Size`, `X-Total-Pages`) already exposed once via CORS in `Program.cs`. Apply this to any new list endpoint by default.
- **Trim input strings used in uniqueness checks** (email, employee/plate numbers, etc.) at the top of the `Service` method, before validation — `dto.Email = dto.Email?.Trim() ?? string.Empty;` (the `?? string.Empty` avoids a nullable-warning on the non-nullable DTO property while still letting `NotEmpty()` correctly reject a null/omitted value instead of throwing). This `?? string.Empty` fallback is only correct for fields that are *always required* — a genuinely optional/nullable field (e.g. `Order.PickupAddress`, only required for one `PickupType`) must trim as `dto.Field = dto.Field?.Trim();` with no `?? string.Empty`, or a caller-omitted `null` silently becomes `""` and fails an unrelated "must be null" conditional rule.
- **CORS** in `Program.cs` is an explicit origin allowlist (`AllowReactApp`) — never replace with `AllowAnyOrigin`.
- **Two distinct failure categories, two distinct exception types** — don't conflate them. A field-level data problem (missing/malformed/duplicate value) is a `FluentValidation.ValidationException` carrying the full failure list, caught by the controller as `400 { errors: [{ property, message }] }`. A status-transition guard (e.g. confirming an already-`Confirmed` `Order`, converting a non-`Confirmed` one) has no "property" to attach to and is instead a plain `InvalidOperationException` with a human-readable message, caught as `400 { message }` — the pattern `ShipmentService.UpdateShipmentStatusAsync` established first and `OrderService` (confirm/cancel/update-when-locked/convert) reuses. Pick whichever this class of failure actually matches; don't force everything through one shape.
- **Multi-entity atomic writes need no explicit transaction API.** `IUnitOfWork.CommitAsync()` just calls `SaveChangesAsync()` once, which already wraps every tracked `AddAsync`/`Update` call made since the last commit in one implicit database transaction. To write several related entities atomically in one `Service` method (e.g. `OrderService.ConvertToShipmentAsync` creating a `Shipment` + its first `ShipmentEvent` + updating the `Order`), just call `AddAsync`/`Update` for each and finish with a single `CommitAsync()` — never introduce `BeginTransactionAsync`/`IDbContextTransaction` for a need this already covers. When one new entity needs the still-unassigned identity of another new entity in the same commit (e.g. `ShipmentEvent.ShipmentId` needs the `Shipment.Id` EF hasn't generated yet), assign the navigation property (`shipmentEvent.Shipment = shipment`) instead of guessing the FK value — EF Core resolves it automatically once the identity is generated.
- **Extending an existing, already-shipped module is a last resort — and when unavoidable, touch the smallest possible surface.** A new module should reference other modules' entities by FK through `IUnitOfWork` rather than modifying them. When a new module's core operation genuinely requires a prior module's entity to gain something (e.g. `Order` conversion requires `Shipment` to know which `Order` produced it), add the single new column needed (`Shipment.OrderId`, nullable — forced nullable by pre-existing seed data and the still-active direct-creation endpoint, see `specs/006-orders/research.md` Decision 2) and nothing else; never restructure the existing entity's own fields to absorb the new module's data. Module `007` extended `ShipmentEvent` itself this same way — 4 new nullable/required columns via `AddColumn<>()` only, no `DropColumn`/`AlterColumn`/`RenameColumn` — when a migration constraint requires "additive only," that means the generated migration's `Up()` method contains no drop/alter/rename calls against the existing table, not just "no data loss."
- **Reuse an existing shared validator/guard mechanism instead of writing a parallel one for the same concern.** `ShipmentTransitionValidator`/`StatusTransitionContext` (module `001`) is the single source of truth for which `ShipmentStatus` transitions are legal. When module `007` added a new status (`OutForDelivery`) and a new service (`ShipmentEventService`) that also needs transition legality, it injected the *existing* `IValidator<StatusTransitionContext>` and added two new branches to `BeAValidTransition` — it did not create a second, parallel transition validator scoped to the new module. Only one file governs `Shipment.Status` legality, no matter how many services end up changing it.
- **A status-transition *check* and a plain equality *gate* are not the same thing — don't force a no-status-change precondition through the transition validator.** `RegisterDeliveryAttemptAsync` requires the shipment to *already be* `OutForDelivery` before accepting a delivery-attempt event, but a delivery attempt never changes `Shipment.Status`. Routing that requirement through `BeAValidTransition(CurrentStatus, NewStatus: OutForDelivery)` would be wrong — it would incorrectly *pass* for a shipment merely `InTransit` (since `InTransit → OutForDelivery` is a legal transition for the sibling operation that actually performs it), silently admitting a delivery attempt for a shipment that was never marked out for delivery. When a precondition is "must currently equal X," assert that equality directly; only call the transition validator when the operation is actually changing the status.
- **A discriminated-union response DTO for public vs. internal consumers must omit sensitive fields from the shape itself, not null them out at runtime.** `ShipmentEventDto` (operational, includes `EmployeeId`) and `TrackingEventDto` (public, no `EmployeeId`/`Id`/`CreatedAt` — module `007`'s `GetTrackingAsync`) are two separate DTO classes mapped from the same `ShipmentEvent` entity via two separate `CreateMap<>` calls, not one shared DTO with a field conditionally nulled for the public path. A structural omission can't regress by accident the way a runtime "remember to null this" can.
- **No DTO class inheritance anywhere in this codebase — not even when two DTOs share almost every field.** `UpdateEmployeeDto`/`CreateEmployeeDto`, and now `RegisterDeliveryAttemptDto`/`RegisterEventDto` (module `007`), are independent flat classes with duplicated fields, never `A : B`. When two operations genuinely need to "inherit" validation rules (e.g. a shared existence/active-status/role check), put that shared logic in one private `Service`-layer helper called by both methods (`ValidateBusinessRulesAsync`, `ValidateEmployeeAsync`, ...) — the same helper-sharing pattern already used for DB-dependent rules — rather than introducing FluentValidation's `Include()` composition, which would require the first DTO inheritance hierarchy in this solution just to satisfy a same-type constraint.
- **A new route prefix can coexist with an older, differently-cased one on the same conceptual resource — don't rename the old one to match.** `ShipmentEventController` lives at `/api/shipments/...` (plural) alongside the pre-existing `ShipmentController` at `/api/shipment/...` (singular, module `001`/`002`). The mismatch is accepted and documented, not "fixed," because renaming the older route would break an already-shipped contract for consistency's sake alone.
- **This solution has no authentication/authorization middleware anywhere — don't add `[Authorize]`/`[AllowAnonymous]` decoration for a policy that doesn't exist.** Every endpoint across all 7 modules is already effectively anonymous. If a plan input calls for `[AllowAnonymous]` on a specific endpoint (module `007`'s public tracking endpoint did), the attribute is correctly omitted rather than added as inert, unsupported-by-anything documentation — note in the XML doc comment that the endpoint is intentionally public instead. If auth infrastructure is ever added to this solution, that is the point at which real `[Authorize]`/`[AllowAnonymous]` attributes start appearing, not before.

### JSON enum serialization gotcha

There is **no global** `JsonStringEnumConverter`. `ShipmentStatus` therefore serializes as a plain number in `Shipment` endpoints (existing, unchanged behavior). The `Branch`/`BranchSchedule`/`Employee`/`Vehicle`/`Customer`/`Order`/`ShipmentEvent` DTOs instead apply `[JsonConverter(typeof(JsonStringEnumConverter))]` **per property** on their enum fields (`Type`, `DayOfWeek`, `Role`, `CustomerType`, `OrderStatus`, `ServiceType`, `PickupType`, ...), so those specific fields accept/return enum names (e.g. `"Hub"`, `"Driver"`, `"Business"`) without affecting `Shipment`'s contract. Do the same (per-property, not global) if a new enum needs string JSON representation. Also note: `TimeOnly` fields (`opensAt`/`closesAt`) require `HH:mm:ss` in JSON — `HH:mm` without seconds fails deserialization.

**Apply the converter to every DTO that carries the enum, not just the response DTO.** The `006-orders` module initially added it only to the output `OrderDto` and forgot the input `CreateOrderDto`/`UpdateOrderDto` — every `POST`/`PUT` sending `"serviceType": "Express"` then failed JSON deserialization (System.Text.Json defaults to expecting a raw number without the converter), even though the response side looked correct. When a DTO has both an input and an output shape for the same entity, check both for the attribute.

### Type-discriminated entities (Table Per Type)

`Customer` (`Individual`/`Business`) is this solution's first — and so far only — type-discriminated entity, modeled as EF Core **Table Per Type**: an abstract base entity (`Customer`) mapped to its own table, plus one concrete subtype per variant (`IndividualCustomer`, `BusinessCustomer`), each mapped with its own `.ToTable(...)` in its own `IEntityTypeConfiguration<T>`. Follow this shape for any future type-discriminated entity rather than a single flat table with nullable per-variant columns:

- The base entity keeps a real, persisted `Type` discriminator property (`HasConversion<string>()`, same as every other enum) even though EF's TPT join already encodes the concrete type — this keeps common list-filtering (`x.Type == type.Value`) cheap on the base table instead of forcing a join.
- **The discriminator is fixed at creation and never appears in the Update DTO at all** — not even as a field that gets rejected if changed. `UpdateCustomerDto` has no `Type` property, so a type change is impossible by construction, not by a runtime check.
- Because the persisted type isn't visible to the Update DTO, FluentValidation can only validate the *shape* of whichever fields are present on update — it cannot decide which variant's fields are *required* without a DB round-trip. That decision (which fields are required/forbidden for this record's actual type) is resolved in the `Service`, after loading the entity and switching on its runtime type (`is IndividualCustomer` / `is BusinessCustomer`), the same way DB-dependent uniqueness checks already are.
- AutoMapper stays output-only but needs the `Include<TDerived, TDto>()` + `AfterMap` pattern to populate a discriminated-union response DTO (e.g. `CustomerDetailDto.Individual`/`.Business`, only one ever non-null): `CreateMap<Customer, CustomerDetailDto>().Include<IndividualCustomer, CustomerDetailDto>().Include<BusinessCustomer, CustomerDetailDto>();` then a separate `CreateMap<TDerived, CustomerDetailDto>().AfterMap(...)` per subtype. Calling `_mapper.Map<CustomerDetailDto>(entity)` resolves to the correct derived map automatically from the entity's runtime type.
- `ICustomerRepository`/`IBaseRepository<Customer>` needs no extra methods — EF Core 8 translates base-type queries (including `is IndividualCustomer`/`is BusinessCustomer` predicates) against a TPT hierarchy into the necessary joins automatically.

### Sequential human-readable identifiers

`Order.OrderNumber` (`ORD-YYYYMMDD-XXXX`) and the `Shipment.TrackingNumber` values generated by `OrderService.ConvertToShipmentAsync` (`TRK-YYYYMMDD-XXXX`) follow the same pattern: count same-day rows via the existing generic `CountAsync(filter)` (`x.CreatedAt >= todayUtc && x.CreatedAt < todayUtc.AddDays(1)`), add 1, format with `.ToString("D4")` (never truncate — let a 10,000th-in-one-day order grow past 4 digits rather than erroring or colliding). No dedicated sequence table or locking is introduced for this — it's a small, accepted, documented race condition under true concurrency (see `specs/006-orders/research.md` Decision 8), not an oversight. Reuse this exact approach for any future `XXX-YYYYMMDD-NNNN`-style identifier rather than adding new machinery.

The same `CountAsync(filter) + 1` idea also covers sequences scoped by **parent record** rather than by date: `DeliveryAttempt.AttemptNumber` (module `007`) is `await _unitOfWork.DeliveryAttemptRepository.CountAsync(x => x.ShipmentEvent.ShipmentId == shipmentId) + 1` — no `ShipmentId` column exists directly on `DeliveryAttempt` (only `ShipmentEventId`), so the filter reaches the parent through the `ShipmentEvent` navigation property; EF Core 8 translates that into the necessary join with no extra repository method needed. Same accepted-race-condition caveat applies at this scope too.

## Spec-driven development

Features are built via Spec Kit (`.specify/`, `/speckit-*` slash commands): each feature gets a `specs/<NNN-feature-name>/` directory with `spec.md` → `plan.md` → `tasks.md` (plus `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, `checklists/`). `.specify/memory/constitution.md` is the authoritative governance document for this repo (framework/dependency/architecture/change-size rules) — consult it before making structural decisions; the summary above reflects it but isn't a substitute for reading it directly when in doubt.
